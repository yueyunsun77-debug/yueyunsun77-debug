本版依据最新职责说明、《功能逻辑分析模块接口需求.md》、MBSE_app与指定服务器仓库整理，替代V1.0。统一以“功能逻辑架构数据”称呼板块二产出。本文核对了源代码、模型及现有测试文件，未连接实际服务器联调，也未重新运行依赖模型的完整流程；研究方案与当前实现分别说明。

## 一、模块定位与职责边界

板块二接收板块一补全并确认的功能点与功能点关系，通过语义聚类、功能分组、关系归属分析和逻辑连接处理，生成功能逻辑架构数据，为物理架构组件选型及连接布局提供输入。

对外服务对象为“物理架构组件选型及连接布局模块”。根据最新接口需求，板块二承担逻辑架构生成、输入补全两个对外接口。功能逻辑分析模型内部在服务器上进行本地联调，内部服务调用与对外HTTP契约分别管理。

板块二向板块三周瑜璇同学交付输出JSON。SysML v2转换、建模工具导入及校验由板块三负责，不再列入板块二的实施任务或完成指标。板块二负责JSON的结构、引用和来源一致性；双方交付方式、版本标识及回执另行约定。

## 三、细化设计方案

### 3.1 总体处理流程

![板块二总体流程](01_板块二总体流程.png)

内部处理接收已补全的功能图，不再次解析原始资源。对外生成入口应将完整上下文适配为内部输入模型，再将聚类归属按功能ID聚合为逻辑分组。需要进一步补全时走独立补全流程，未确认的候选不应直接替换已确认输入。

### 3.2 输入模型与功能图校验

内部ClusteringInput包含function_points和relations数组，功能点至少一个，关系允许为空。功能点采用function_id、name、description、target、effect、domain、inputs、outputs等标准字段；输入输出项为字典，如{"name":"电池温度"}。

关系采用left_function_id、right_function_id、type、confidence和source_refs。type为开放字符串或null，不是封闭编码枚举；confidence可为空，非空时限定0至1；source_refs为来源信息，模型要求提供该字段，允许空数组。

聚类服务检查重复功能ID、不存在的关系端点及全部为空的语义文本，异常抛出ClusteringInputError。当前服务不会主动去重关系，也不统一改写关系type。对外适配必须保留原功能ID，不应为可读性自行重编号而破坏追溯。

### 3.3 多字段语义表征与BIRCH聚类

服务器实现递归提取功能模型中的语义字符串，排除function_id、source_refs、extras及JSON字段名。输入语义包括名称、描述、作用对象、效果、触发、约束、领域、输入输出、能力、场景、工况和前后置条件等。经jieba分词、停用词过滤、TF-IDF和L2归一化后执行BIRCH。

默认参数为birch_threshold=0.6、branching_factor=50、n_clusters=None，可在Python服务构造时覆盖。threshold控制子簇半径，不是余弦相似度门槛。当前特征转为稠密矩阵，大样本需关注内存和相似度计算开销。

聚类后建立function_id到cluster_id的映射，用关键词规则生成子系统名称和功能簇释义。cluster_id是本次运行编号，不是跨批次稳定ID；辅助命名需要工程复核，也不能直接作为物理组件选型结论。

### 3.4 功能逻辑架构数据的组织

“功能逻辑架构数据”是整体交付名称。下述字段是当前内部结果的不同维度，不再以输出表数量定义板块二成果。

| 数据维度与当前字段 | 主要内容及用途 | 交付时的注意事项 |
| --- | --- | --- |
| 功能归属 architecture_layers | 功能ID/名称、层级、子系统、簇名称和簇ID | 当前层级固定component，未形成显式系统—子系统—组件三级树 |
| 功能关系 clustered_relations | 原关系及来源，增加left_cluster/right_cluster | 保留端点ID和type，不因分组重新解释关系 |
| 逻辑连接 logical_connections | 连接编号、源/目标名称、端口、关系类型、流对象、簇和证据 | 当前缺少端点ID，跨模块交付建议补齐，避免同名功能混淆 |
| 评价 metrics | 样本/簇数量、几何与语义指标、孤立簇比例和评分 | 无法计算时为null，不是0分，也不是正确率 |
| 处理配置 processing | 功能/关系数量、阈值、分支因子和语义字段说明 | 用于解释本次结果，不能代替任务版本管理 |

对外需求规定逻辑架构是“包含function_id集合的功能分组”。可由architecture_layers按cluster_id聚合获得该视图，但这一步尚需对外适配层。给板块三的JSON可同时保留关系、连接和来源信息。最终Schema、任务及版本字段须双方确认，不能把建议格式当成既定契约。

### 3.5 功能关系与逻辑连接处理

![功能关系与逻辑连接处理流程](02_关系与拓扑生成流程.png)

当前服务对每条输入关系附加两端簇标签，并生成相应逻辑连接记录，两者在该阶段一一对应。重复关系不会被本服务自动删除。

仅type为“数据流”或“DATA_FLOW”时读取源outputs和目标inputs中的name，优先匹配去空格后相等的信号名。没有同名匹配则回退到各自首项，缺失端填“—”，流对象取源端口。其他关系类型的端口和流对象均为“—”，保留原始语义，不伪装为数据连接。

此策略尚未完成数据类型、单位、接口协议和一对多信号匹配。首项回退不表示连接已获工程确认，建议后续输出匹配方式和待确认标记；非数据流关系也不能因无流对象而丢弃。

### 3.6 聚类评价与后续研究

当前服务器计算inner_similarity（簇内点对平均余弦相似度）、inter_similarity（簇质心间平均余弦相似度）、isolated_cluster_ratio（单元素簇数/总簇数），并在脚本条件满足时计算Silhouette和DB指数。遇单元素簇时当前脚本不会计算后两项，不能误写为指标理论本身禁止单元素簇。

architecture_score采用inner_similarity/inter_similarity，仅在指标有效且分母大于1e-6时计算；该比值不限定0至1。当前metrics没有Purity字段，不应声称已实现组会提出的0.35×InnerSim + 0.35×(1−InterSim) + 0.30×Purity。

后续固定数据和前处理，比较阈值变化下的分组、碎片化与业务解释性；人工域标签具备后再研究Purity及权重敏感性。现阶段不预写“权重稳健”或“架构正确”等结论。共同领域文本可能影响功能差异，也应纳入特征分析。

### 3.7 处理伪代码

以下对应当前服务器聚类内核；输出契约为ClusteringResult。

```text
async 生成功能逻辑架构数据(source):
    points ← 校验ClusteringInput(source).function_points
    建立point_by_id；若功能ID重复则报错
    校验relations的端点均存在；复制关系
    texts ← 递归提取语义值(points，排除ID、来源、extras)
    tokens ← jieba分词并去停用词(texts)
    若全部语义为空：报错
    X ← L2归一化(TFIDF(tokens))，转为稠密矩阵
    labels ← BIRCH(X, threshold=0.6, branching_factor=50)
    cluster_by_id ← 功能ID与labels关联
    生成辅助名称和architecture_layers
    对每条relation：
        保留原字段并附加两端簇 → clustered_relations
        若type属于{数据流, DATA_FLOW}：
            按name同名优先、首项回退选择端口
            flow_object ← 源端口
        否则：端口及flow_object ← —
        构造logical_connections，保留类型、置信度和来源
    返回ClusteringResult(归属、关系、连接、metrics、processing)
```

对外适配新增设计为：接收上下文→展开functions映射→调用聚类服务→按cluster_id聚合function_ids→按双方约定返回逻辑架构JSON。该适配流程尚未注册为/generate_logical_arch路由。

## 四、关键接口（按最新需求重写）

### 4.1 接口范围与共同上下文

本章仅以最新接口需求中的第2、第3接口为板块二对外要求，服务于物理架构组件选型及连接布局模块。第1项输入资源规范化不列为板块二新增接口；服务器内部编排、补全和聚类服务之间是本地调用关系。

共同数据包PhysicalArchGenContext包含task_id、system_description、functions、function_models、requirements、requirement_models、logical_architecture、attachments及function_relations。functions是function_id到Function的字典，requirements是req_id到Requirement的字典，键须等于对象内ID。当前模型采用严格校验并拒绝未知顶层字段，不直接接受旧id/event格式。

需求指出连续对话可能不重复之前信息，但当前代码未按task_id实现持久会话上下文合并。review_id仅用于补全候选确认，不能替代通用task_id增量会话。仅凭task_id恢复完整输入的行为仍需实现或另行约定。

### 4.3 对外接口二：输入补全

路径为POST /complement_arch_gen_context。输入为上下文、提示文字和生成选项；业务输出为新上下文、是否需要补全的布尔标志及说明。

**需求与实现的差异：**需求规定options.only_check=true只判断，不实际补全。当前ComplementArchGenOptions仅支持review_id和accept_completion，禁止额外字段，传only_check会得到422。实际代码是“候选预览—人工确认”，不能写成已支持only_check；后续须明确将检查选项与复核流程如何结合。

| 当前调用阶段 | 请求内容 | 行为与响应 |
| --- | --- | --- |
| 候选预览 | physical_arch_gen_context完整上下文；prompt可空；options为{} | assess评估并在副本构造候选，响应中的原上下文不被替换 |
| 存在可接受候选 | 同预览请求 | needs_completion=true，返回说明、review_id、completion_preview及proposed_physical_arch_gen_context |
| 无可接受候选 | 同预览请求 | 返回原上下文、needs_completion=false及说明，无需确认 |
| 接受或拒绝 | options中给review_id及accept_completion=true/false；可不再提供上下文 | 接受返回候选新上下文；拒绝返回原上下文，字段均为physical_arch_gen_context |

当前预览请求示例：

```json
{
  "physical_arch_gen_context": {
    "task_id": "thermal-case-001",
    "system_description": "电池热管理系统",
    "functions": {
      "fn-monitor": {
        "function_id": "fn-monitor",
        "name": "监测电池温度",
        "description": "采集电池温度数据。",
        "target": "电池温度",
        "effect": ["获得温度数据"],
        "domain": "电动汽车热管理"
      }
    },
    "function_relations": []
  },
  "prompt": "检查温度控制闭环是否完整",
  "options": {}
}
```

当前确认请求示例：

```json
{"options":{"review_id":"预览返回的复核标识","accept_completion":true}}
```

响应字段包括physical_arch_gen_context、needs_completion、completion_description及可选review_id、completion_preview、proposed_physical_arch_gen_context。needs_completion表示至少一项建议通过现有置信度、去重和端点等筛选，不表示用户已接受，也不表示发现了所有潜在缺项。prompt限定审查重点，不可单独作为新增事实证据。

review_id在服务进程内存保存30分钟，只能消费一次；重启或多进程转发可能导致复核不可用，尚不保证持久化会话。标识不存在或过期返回404，输入或业务值错误返回422，未处理流程异常返回502。模型配置、服务地址、认证及重试规则以后续部署约定为准。

当前首次评估仍调用补全服务并依赖模型，不能当作无需模型的轻量检查。新增only_check时应保证不写回原上下文，并区分“检查结果”“候选补全”“接受后更新”三种状态。

### 4.4 模型内部的服务器本地联调

已核对内部入口：FunctionClusteringService.cluster(source: ClusteringInput) → ClusteringResult。异步方法通过asyncio.to_thread执行聚类计算；统一编排在补全后适配完整功能图并调用本地服务，不通过HTTP调用旧MBSE_app接口。

结果进入analysis-package.json.clustering，并另存clustering/<clustering_id>/input.json与result.json，运行清单及quality.clustering记录状态。聚类失败时上层可能保留功能图并记录warning，所以编排有响应不等于聚类成功，需检查阶段状态和结果字段。

服务器文档给出的本机调试启动命令为uv run uvicorn interfaces.app:app --host 127.0.0.1 --port 8000；POST /api/unified-runs为统一编排入口，按其multipart资源约定提交，不是独立聚类HTTP接口，也不能替代需求中的/generate_logical_arch。实际地址、端口、认证与模型配置由服务器部署确定，本报告未启动或连接该服务器。

## 五、后续细化与验收

优先新增对外生成路由，接入现有聚类内核并明确分组JSON、上下文写回与错误返回；随后对齐only_check和候选复核流程，确定task_id增量恢复机制。模型内部继续采用服务器本地服务联调，避免将内部函数入口和对外业务协议混写。

算法侧先评价特征字段、阈值及碎片化，具备人工标注后再研究Purity和加权方案。交付侧补充逻辑连接端点ID及匹配标记，与物理架构模块和板块三分别确认Schema。

验收应覆盖重复功能ID、非法端点、空功能集、空关系、重复关系策略、同名信号匹配、首项回退、非数据流不伪造端口、指标null、补全接受/拒绝、过期复核、only_check不改原上下文与task_id增量恢复。后两项属于当前需求目标，尚未实现。本次没有执行以上验收，不填造通过记录。
